# 错误码规范

## 1. 错误码统一定义机制

整个大仓采用**“全局统一 + 服务级定制/覆盖”**的错误码管理机制：
1. **全局错误码**：统一定义在 `api/ecode` 服务中。所有的跨服务共用错误、基础错误，必须在这里统一定义。通过修改 `api/ecode/ecode.csv` 并执行 `waterdrop ecode ./ecode.csv .` 重新生成 `ecode.go`。
2. **服务引用与覆盖**：各业务服务统一引用 `api/ecode` 中定义的错误码常量。
3. **服务内自定义/覆盖**：各服务内部的 `internal/ecode` 目录用来存放该服务特有的自定义错误码。如果某服务需要改变某个全局错误码的文案（例如多语言文案定制），也可以在服务内的 `internal/ecode/i18n.go` 中，注册与全局相同 Code 值的不同文案来实现覆盖。

**【覆盖示例】服务内的 `i18n.go` 必须优先注册默认全局码：**
```go
func init() {
	// 1. 优先注册全局错误码
	Register(map[string]errors{
		"zh-cn": errors(ecode.ZHCNErrMsg),
		"en":    errors(ecode.ENErrMsg),
	})

	// 2. 注册自定义错误码，相同错误码会覆盖全局，达到更换文案目的
	Register(map[string]errors{
		"en":    enRequestErrMsg, // 此处可包含全局的 code，对应不同的 msg
		"zh-cn": zhRequestErrMsg,
	})
}
```

## 2. 错误码空间分配

错误码从 `100000` 开始，按业务域分配，每个业务域给 **1000** 个错误码空间。

| 前缀 | 范围 | 业务域 | 说明 |
|-----|------|-------|------|
| `10` | `100000` - `100999` | 公共/基础 | 通用错误（内部错误、参数非法、限流等） |

> **新增全局错误码前，必须先查本文件确认空间未被占用，再向本文件登记，并同步更新到 `api/ecode/ecode.csv`。**
> **新增服务时，通过 `/service:onboard` 或 `/service:harness` 自动预留码段。**

## 3. 错误响应格式

```json
{
    "code": "110001",
    "msg": "用户不存在",
    "trace_id": "req-xxx-yyy-zzz",
    "datas": {}
}
```

## 4. 错误码登记表

### 公共/基础（`100000` - `100999`）

| 错误码 | 含义 | 登记人 | 登记日期 |
|-------|------|-------|---------|
| 0 | 成功 | - | - |
| 100000 | 服务器开了小差，请稍后重试 | - | - |
| 100001 | 参数错误 | - | - |
| 100002 | 未授权 | - | - |
| 100003 | 无权限 | - | - |
| 100004 | 资源不存在 | - | - |
| 100005 | 限流 | - | - |

---

## 5. 规范约束

- **禁止**：直接返回 HTTP 状态码作为业务错误码
- **禁止**：在不同模块中使用相同的错误码值（除非是在 `internal/ecode` 中故意为了覆盖全局的文案）
- **必须**：新增全局错误码前在本文件登记并更新到 `api/ecode`
- **必须**：各服务内的 `internal/ecode/i18n.go` `init()` 函数必须优先注册全局 `ecode`
- **必须**：错误信息使用中文（面向用户）或英文（面向开发者），不混用
- **必须**：内部错误（100000）不暴露堆栈信息给客户端
