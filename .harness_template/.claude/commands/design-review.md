# 设计门禁执行命令

## 描述
执行设计阶段门禁检查。

## 触发条件
用户输入 `/design:review`。

## 执行动作
1. 加载当前活动的 requirement id。**注意：如果用户输入的命令中自带了需求ID字段，则直接使用该ID，无需询问用户**。
2. 调用 `detail-design-quality-reviewer` Agent。
3. 检查 `design.md` 和 `tasks/features.json`。
4. **【核心协议校验】**：校验 `design.md` 中的设计是否与**用户在 `/design:new` 第一步交互中确认的服务归属和通信协议（HTTP Service 或 gRPC Service）**完全一致。
   - 举例：如果用户确认是 HTTP Service，那么设计中若包含 `.proto` 文件或 gRPC 相关章节，门禁**必须判定为不通过**并拦截。同时检查架构设计中是否严格遵循了 `code-implementation-examples.md` 中对应的样板（HTTP、gRPC 以及统一的数据访问层样板）。
5. 校验是否满足设计门禁其他所有条件（方案覆盖度、设计核心要素完整度、数据库变更、任务粒度等）。
   - **【设计要素完整性校验】**：检查 `design.md` 中是否明确包含了**改动服务范围、整体流程图或流程说明、详细的设计思路、架构方案（含改动代码结构）、可能带来的性能瓶颈点分析**。如果没有，门禁**必须判定为未通过**，并主动进行设计补充（列出初步想法），或者询问用户可以补充哪些点。
   - **【设计要素完整性校验】**：检查 `design.md` 中 DDL的设计是否符合 `context/team/db-design.md` 规范。必须有自增占位主键。如果没有，门禁**必须判定为未通过**，并主动进行设计补充（列出初步想法），或者询问用户可以补充哪些点。
   - 举例：如果表结构 DDL 除主键自带索引和实体表业务ID的唯一索引外，直接生成了带其他普通查询索引的 DDL，门禁**必须判定为不通过**并拦截。设计阶段非主键索引仅做文字建议，如非必要避免使用多列索引。
6. 生成报告并写入 `requirements/{requirement-id}/gate-2-design-review.md`。
7. 输出结果给用户。**注意：如果有DDL变更，提醒用户去生成DAO、IFace及Model的xo文件**。
